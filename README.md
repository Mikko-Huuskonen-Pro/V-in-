

# Väinö

**Traditional operating systems stock drivers. Väinö builds them.**

---

## AI-native driver model

Väinö explores a different model for hardware drivers.

Traditional operating systems accumulate drivers over decades. A driver is usually a permanent software component that must be designed, implemented, tested, and shipped before the operating system can use a device.

Väinö asks a different question:

> What if a driver only needs to exist when a task requires it?

A Väinö driver is therefore not necessarily a permanent piece of the operating system. It can be a small, task-specific implementation generated locally by AI and constrained by the kernel.

The intended model is:

```
Hardware
    │
    ▼
Hardware description
    │
    ▼
Local AI
    │
    ▼
Task / Driver Plan
    │
    ▼
Kernel Policy
    │
    ├── allowed resources
    ├── allowed operations
    └── forbidden operations
    │
    ▼
Generated Driver
    │
    ▼
Validation
    │
    ▼
Sandbox / Capability boundary
    │
    ▼
Hardware
```

The AI does not receive unrestricted access to the system.

Instead, the AI first creates a plan describing the smallest set of resources required to perform the task.

For example:
```text
Task:
    Read a temperature sensor.

Required:
    MMIO read: 0x4004
    Timer: 10 ms

Not required:
    DMA
    Network
    Filesystem
    Other devices
    Kernel memory
    MMIO writes
```
The kernel then decides which capabilities can actually be granted.

The AI may request a capability, but it cannot grant one to itself.

## Standing on Linux's shoulders

Väinö would not exist in its current form without the extraordinary engineering effort behind Linux and its ecosystem.

For more than three decades, Linux developers have built and maintained an enormous body of knowledge about real hardware: drivers, protocols, firmware, hardware quirks, failure modes, and countless devices.

We do not intend to throw that work away: [VSL](https://github.com/Mikko-Huuskonen-Pro/VSL)

Where Linux has already solved a problem well, Väinö can build on it.
The linux-väinö repository provides a path to preserve and use that existing hardware support while Väinö explores a fundamentally different approach to drivers.

> **35 years of engineering is not something to replace. It is something to stand on.**

### Plan, Policy, Implementation

Väinö separates three concepts:

#### Plan
The local AI determines what the driver believes it needs.
OS written in Zig (More information about Zig in Finnish: [zig-book-FI](https://mikko-huuskonen-pro.github.io/zig-book-FI/))

#### Policy
The kernel determines what the driver is actually allowed to do.

#### Implementation
The AI generates the smallest practical driver satisfying the approved plan.

The intended execution pipeline is:
```
 plan
  ↓
request capabilities
  ↓
kernel approval
  ↓
generate code
  ↓
compile
  ↓
validate
  ↓
sandbox
  ↓
run
```

This means that AI-generated code does not need to be trusted simply because it was generated by an AI model.

**The kernel remains the authority.**
**The AI proposes. The kernel decides.**

## Task-specific drivers

The long-term goal is to avoid building a universal driver for every possible device in advance.

Instead, Väinö aims to make hardware support composable from small, constrained building blocks.

A robot may contain an unusual combination of sensors, motors, cameras, buses, and custom hardware. Väinö explores whether local AI can construct the minimal software required to operate that hardware when it is actually needed.

This is inspired by a broader principle:

**Do not ship everything that might be needed. Construct the smallest environment required for the task.**

The goal is not AI-generated code with unlimited privileges.
The goal is AI-generated code operating inside a kernel-defined world of strict rules and limited capabilities.

## Prior Art & Inspiration

Väinö does not start from the assumption that automatic device-driver generation is a new idea.

Researchers have explored device-driver synthesis for many years. In particular, the Termite project demonstrated that device drivers could be synthesized from formal specifications, while Termite-2 explored user-guided synthesis to address the limitations of fully automatic generation.

Väinö is inspired by this line of research, but asks a different question:

> Can a local AI reduce the specification burden by turning ordinary hardware documentation and a task into a constrained driver plan, while the kernel remains the authority over capabilities and execution?

The goal is not to replace or dismiss previous work.
It is to continue the experiment with the tools available today.

---
### Pioneers

- **Termite / Termite-2** — device-driver synthesis and user-guided synthesis
- **User-Guided Device Driver Synthesis** — Ryzhyk et al., OSDI 2014
- **Driver isolation research** — Nooks, microkernel-based drivers, sandboxing, and related work

These projects established important foundations for thinking about drivers as something that can be synthesized, constrained, and isolated.

**Väinö stands on their shoulders.**

## Väinö 1.0 Gate

Väinö 1.0 is defined by a machine-checked set of requirements.

The project is not considered ready for 1.0 simply because the maintainers decide that it feels ready.

The repository contains the canonical 1.0 requirements in:
`docs/1.0.md`

Every requirement must be satisfied before the Väinö 1.0 Gate turns green.

The GitHub Actions workflow checks this gate on every change.

Until every requirement is satisfied:
```
Väinö 1.0    🔴 NOT READY
```

When every requirement is satisfied:
```
Väinö 1.0    🟢 READY
```

The initial requirements are:
```text
Väinö 1.0 requires:

[ ] Kernel boots on x86_64
[ ] Interrupt handling works
[ ] Virtual memory works
[ ] Processes work
[ ] IPC works
[ ] Capability system works
[ ] Drivers are isolated
[ ] Local AI can generate a driver
[ ] Generated driver passes validation
[ ] Generated driver runs sandboxed
[ ] Hardware can be dynamically added
[ ] At least one real robotic device works
```
The long-term intention is for these requirements to become backed by actual automated tests rather than manual claims.

**1.0 is not a promise. It is a state the system must prove.**

## Build

```bash
# Download Zig 0.16.0
# curl -fsSL https://ziglang.org/download/0.16.0/zig-x86_64-linux-0.16.0.tar.xz | tar xJ

# Build kernel
zig build

# Create ISO (dependency: xorriso + curl + cc)
zig build iso

# Start QEMU (dependency: qemu-system-x86_64)
zig build run

# Run tests
zig build test
```
